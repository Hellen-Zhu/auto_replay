# OREO UAT Replay - Full Handover Notes

> The complete, detailed notes. `CLAUDE.md` at the repo root is the short version that is loaded into every session; read the section of this file you need before changing that area.

## 1. Background and goal

- Project: UAT testing of OREO, a bank-internal system managing the full lifecycle of non-flow FX structured products (TARF, DCD, KO Forward, etc.).
- Role: the user is QA.
- Goal: **QA runs a case locally with Playwright → a "case file" (JSON) is exported automatically → the PO, without writing code or installing anything, double-clicks to really replay that case in the browser on their own computer, to reproduce issues or repeat acceptance.**
- Current status: **the MVP is complete and verified** (log in → land on the Trades page → verify the top-right corner shows the current user), end to end on the mock pages and triggered successfully on the company machine. Trade creation, the checker's approval / rejection and trade cancellation are written and pass on the mock; on the real system they are only partly run (section 10, items 4 and 5). Next: connect to the real system.

## 2. Key decisions already made (do not overturn lightly)

| Decision | Reason |
|---|---|
| Use Playwright (cases in TypeScript, runner in plain JS) | Best locators, auto-waiting and trace capability |
| Export **JSON step data**, not code | The PO runs data only: safe and easy to audit; waits, screenshots, browser, etc. are controlled centrally by the runner |
| **QA runs and PO replays share `core/actions.js`** | Guarantees "what ran when it was recorded is exactly what runs on replay" |
| Record at the "action layer" instead of recording mouse clicks | The system is stateful (trade IDs differ every time); click recordings cannot be re-run |
| Server address, accounts and passwords live only in `config.local.json` | Never in code, case files or Git (the real IP seen in screenshot URLs must not appear in the repo) |
| **Case data lives in `testdata/*.json`** (committed) and travels inside the case file as `params` | Different cases need different parameters, so they cannot all sit in one config file; the PO gets the data with the case and can change it for a run. Config is for the environment only |
| The PO side is a **portable folder**: portable `node.exe` + `runner` + `@playwright/test` | The PO cannot install software; uses the machine's own **Edge** (`channel: msedge`), no browser download |
| **No video** by default | Video depends on Playwright's ffmpeg; the company intranet cannot resolve `cdn.playwright.dev`, so the download fails |
| Packaging **copies the local node.exe** instead of downloading Node | The company intranet cannot reach nodejs.org |
| Locators **prefer `data-testid`** | Explicit user requirement; developers already provide testids on key controls |
| **Locators are the E2E project's element JSON**, copied as it is into `elements/` and used by name: `element('new_trade.book_btn')` | Explicit user requirement: do not convert the Java project's locators one by one; a locator is maintained in one place |
| **A trade a case needs beforehand is created through the API**, as an `api` step of the case, sent with Playwright's own request client (`page.request`). The API has no login: the sender is the header `X-User-Id` = that role's e-mail from the local config | Explicit user requirement. Lifecycle events (cancel, approve, step in...) all start from an existing trade; the E2E project provisions it through the API too. Its `RestUtil` is a company-internal Java library and is not used |
| **`FX_CO` is `FX_PSCRIPT`, `FX_FSB` is `FX_PSCRIPT_FSKO`** | Stated by the user: the E2E project's features still list the old names in their Examples; this repo uses only the new ones (registry, case IDs, `testdata/dat/<PRODUCT>/<PRODUCT>.dat`, API `productId`). Do not add the old names as separate products |
| **English only** across the repo | Explicit user requirement: no Chinese in code, comments, messages, file names, docs or case files |
| Rejected approaches | Intranet server + live noVNC view (user found it too complex); packaging as a Java jar; pure click record-and-replay |

## 3. Architecture

```
QA:  tests/*.spec.ts ─► framework/flows/   ─► framework/pages + components + api ─ui.xxx─► framework/ui.ts (execute + record)
     (case: scenario)   (flow: BDD steps)      (locators / requests + atomic operations)  │ calls
                                                                                    ▼
                                                                              core/actions.js  ◄── shared execution core
                                                                                    ▲
PO:  run-case.bat → runner/runner.js ──reads cases/**/*.json, calls step by step───┘
```

- Page Object Model in three layers, each calling only the one below (QA side only; the case format and the runner know nothing about it). **Page / component** (`framework/pages`, `framework/components`): owns locators as `protected readonly` fields and exposes atomic operations built on `this.ui.xxx` (one field, one button, one dropdown value, one check); a page exposes the components it contains as public fields (`newTrade.confirmDialog.confirm()`); a form with many fields is a table plus one generic operation (`newTrade.setField(name, v)`). **Flow** (`framework/flows`, one class per business domain extending `BaseFlow`, reached through the `flows` fixture as `flows.<domain>.<step>()`): business steps, i.e. the Given / When / Then groups and the atomic operations inside them; each takes an optional keyword. **Case** (`tests/`): only the scenario's steps, each wrapping `flows.<domain>.xxx(...)` calls, and data. `App` (`framework/app.ts`, the `app` fixture) holds one instance of every page and of `TopBar`. The refactoring was verified by exporting all ten cases on the mock before and after: the steps are identical.

- API objects (`framework/api`, QA side only) are the same layer as pages and components: a class per API area extending `BaseApi` holds its requests as `static` (`TradesApi.submit`) and one atomic operation per request, built on `this.ui.api(...)`; `this.as(role)` gives the `X-User-Id` header as `cfg('accounts.<role>.email')`. A flow composes them (`flows.tradeProvisioning.provisionLiveTrade(product, data)`: the maker submits, the checker approves; returns the trade ID); a case never calls them. `ui.api` records an `api` step (section 5) and returns the saved response fields, which are tracked as variables like a `read`. API steps are for preparing data: the `When` and the `Then` of a case stay in the browser, or the PO's replay shows nothing.
- **The PO's runner always uses the real risk engine** (explicit user requirement: the PO gets one fixed setting and no option to change it; the user's word was "true", taken to mean the real engine). `FIXED_SETTINGS = { riskEngine: 'real' }` in `runner/lib/settings.js`: `main()` writes it over the loaded config in memory, `requiredOf` leaves such a key out of what is shown under "Settings for this run", asked for or changed with `C`, the hint to set `"mock"` is left out of a failed step (`ctx.fixed`), and `build:portable --with-config` drops the key from the packaged config. So what the paragraph below says about the runner (`C` changes it, the `mock` notes on the screen and in the report) applies to QA's Playwright run only, which still reads `riskEngine` from `config.local.json`; the mock notes of the runner are still in the code but cannot occur. Also `npm run replay` is fixed to `real`. To give the PO the mock instead, change that one value. Verified on the mock: with a config that says `"mock"` and the risk endpoints answering 503 the replay fails with the 503 and the setting is not listed; with the endpoints up it passes. **Not on Windows / Edge.**
- **Risk engine mode** (explicit user requirement: mock or real by configuration, like the E2E project's "configured risk engine mode"). Booking a new trade and triggering an event on a trade make the page call a third-party risk calculation before the confirmation dialog opens; when that engine is slow or down the case fails. `riskEngine` in `config.local.json` is `"real"` (default) or `"mock"`; any other value fails the step. The click that starts the calculation is recorded with the request it triggers (`ui.clickAndAwait(target, request)`, a `request` on the `click` step, section 5; the requests are in `framework/risk-engine.ts`: `RiskCalculation.forNewTrade()`, `RiskCalculation.forTrade(tradeId)`). `real`: the step waits for the system's answer, up to `timeouts.response` (default 60000 ms), and fails on any answer other than 2xx with a hint to the setting. `mock`: the request is answered in the browser (`page.route` + `route.fulfill`, removed again after the click) with the success answer of the E2E project's test data and never reaches the system. The mode is not in the case file: the same file runs either way, QA and PO each with their own config. The case lists `riskEngine` in `requiredConfig`, so the runner shows it under "Settings for this run" and `C` changes it; a run with a mocked request says so on the screen (`NOTE: riskEngine is "mock" ...`), in the step text (`MOCKED`), in `result.json` (`mocked`) and at the top of the report. Verified on the mock in both modes, also with its risk endpoints answering 503 (`MOCK_RISK_ENGINE=down`: `real` fails with the status, `mock` passes), and with a probe for a request to another origin with a preflight. **Not run on the real system.**
- Data-driven cases (QA side; a row may also list `use` blocks, merged after `defaults` and before the row's own values): `testdata/common.json` is a flat object shared by all files; `testdata/<name>.json` is `{ "use": [...], "defaults": {...}, "cases": [ { "id": ..., ... } ] }`, all optional. `use` lists shared blocks: `"use": ["given-trade"]` takes `shared.given-trade` of `testdata/common.json`, a flat object of values that several specs share but not all of them (the API data of the trade a lifecycle event starts from). A case is merged common → shared blocks, in the order listed → defaults → row (the row wins). A block that does not exist, or a name with anything but letters, digits, `_` and `-`, fails the case. **Data is matched at run time by case ID** (explicit user requirement): a test title starts with its case ID in `[ ]`, which the spec may build (`[TC-TRADE-CREATION-${product}-UI-001]`); the row `id` in testdata is the full ID (`TC-TRADE-CREATION-FX_TRF-UI-001`); the `testData` fixture (`const data = testData<TradeCreationData>()`) looks the title's ID up in `testdata/<spec file name>.json`. A row exists only for a case whose values differ from the shared ones (explicit user requirement: no rows that hold nothing but an id); without a row the case gets common + defaults. Do not generate the cases by looping over the testdata rows. The case hands the data to the flow. In the flow `const p = this.params(data)`: `p.xxx` is recorded as `${param:xxx}` and its value is written to the `params` block of the case file (only parameters that are used, in order of first use); what decides the scenario (the product) stays in the spec, is passed to the flow as a plain argument and is recorded literally. Pages and components are unaffected: their operations take a `Val`.
- **One test data file for what specs share** (explicit user requirement: too many files under `testdata/`). The blocks that were `testdata/shared/<block>.json` are the entries of the `shared` object of `testdata/common.json` (`{ "counterpartyName": ..., "shared": { "given-trade": {...}, "allocation": {...}, ... } }`); `use` names them as before. `findCase` takes `shared` out of the common values (it is never case data), fails a block that is not an object or does not exist (`"use" names "X", but "shared" of testdata/common.json has no such block`). Nothing else changed: a spec still has its own `testdata/<spec name>.json` (matched by name, which keeps the per-event data next to its spec). The alternative, one file for all specs, was offered to the user and not built.
- **Case data is shown only when the run needs it** (explicit user requirement: an allocation into two showed the counterparties of subtrade 3 and 4). `notRunWith(steps, params)` (`core/lib/values.js`) returns the params and config entries that only actions which do not run with this data use (a `when` that does not hold: `in` or `empty`); a param that a condition names always stays, and so does a param named in a step line (the product of a case run on a given trade). `notNeededOf(doc, params)` in `runner/lib/settings.js` uses it for "Settings for this run", "Case data", what is asked, `result.json` `caseData` and the report, and it is worked out again after every change, so choosing `3` for `allocationWays` brings back the rows of subtrade 3. It replaces the trade-ID-only rule (`onlyWhenEmptyOf`, kept).
- **Case data that must differ** (explicit user requirement: a trade is never allocated twice to the same counterparty). The case file may have `"distinct": [["subTrade1CounterpartyName", "subTrade2CounterpartyName", ...]]`: in each group no two values that the run needs may be equal (trimmed, case ignored; an empty value or one the run does not need is not compared). Writer: `ui.distinct(...vals)` (`framework/ui.ts`, params only), which also fails QA's run when the test data has two equal values (`Test data A and B are both "v": they must be different`); the allocation flow calls it for all four rows, so a case file is valid for every number of ways. Runner: `distinctProblem(doc, params)` in `runner/lib/settings.js`; on a console the run does not start until a value is changed, `checkCase` refuses such a case in a batch or with piped input. An older runner ignores the field, so `FORMAT_VERSION` stays 15. The allocation's counterparties are now `10 AM JAK`, `11 AM GMT`, `3 PM HK`, `1330 ATH` (from the user's photo of the real dropdown).
- Element locators (QA side): `elements/` mirrors `src/test/resources/elements` of the Java + Cucumber E2E project, with the same two folders (`pages/`, `components/`) and file names; each file is a list of `{ "name": "new_trade.book_btn", "lookupDetails": { "findBy": "testId", "value": "create-trade-book-btn" } }`. `element(name, extra?)` (`framework/elements.ts`) turns a name into a `Target`; `extra` (`inner`, `nth`, `exact`) adds what the element files do not know, above all `{ inner: 'input' }` (or `{ inner: INNER_INPUT }`, which also matches a multi-line field), since they only locate the host of a control. Files are read once, on first use; an unknown name, a name defined differently in two files or an unsupported `findBy` (only `testId` so far, `FIND_BY`) fails the case with a clear message, and only for elements that are really used. `npm run sync:elements -- <E2E project>` (or `OREO_E2E_DIR`) mirrors the files (added / changed / removed; it aborts without copying when a file seems to contain a server address) and then checks `elements/` against `framework/`: used names that are undefined fail it, hand-written testids that an element defines are listed with the `element('...')` to use. `OREO_ELEMENTS_DIR` points the loader at another folder. Nothing changes for the PO: a case file holds resolved targets and `elements/` is not packaged. No dynamic (placeholder) locators yet: the E2E project has none that are needed.
- **The dat files are under `testdata/dat/`** (explicit user requirement: with the other test data, not in a top-level `data/` folder as before). `DATA_DIR` in `core/actions.js` is the one place that names the folder (`resolveDataFile`, `build-portable.js`). A case file exported while the files were in `data/` still runs: `dataPath` reads a path that starts with `data/` from `testdata/dat/` (`resolveDataFile`, `dataFilesOf`, so the runner's lists work for it too). The package gets `testdata/dat/` only, never the JSON test data. Verified on the mock: QA run, replay of the exported file and of a copy with the old path. `npm run build:portable` was not run after the move.
- **Dat files: a folder per product, the file is case data** (explicit user requirement: a product has several dat files, variants of its structure, and the PO chooses one). Layout `testdata/dat/<PRODUCT>/<file>.dat`; the default file is `testdata/dat/<PRODUCT>/<PRODUCT>.dat` (`defaultDatFile`, `datFile(product, file?)` in `framework/products.ts`). A variant is data, never a product, a capability or a case of its own: a case is added only when its steps or checks differ. The file name is the optional `datFile` of the data object (`TradeCreationData`, `TradeProvisioningData`): the creation flows and `flows.tradeProvisioning` make it the case data `datFile` (`this.caseData`) and upload / send `testdata/dat/<product>/<datFile>`; without it the product's default file `<PRODUCT>.dat` is that case data (explicit user requirement: the per-product creation cases `-UI-001` to `-003` recorded it literally before, so the PO could not choose a file there; their step holds `testdata/dat/<PRODUCT>/${param:datFile}`, the product stays literal, and the step line is `I upload the <PRODUCT> dat file ${param:datFile}`). Verified on the mock: QA export of `TC-TRADE-CREATION-FX_TRF-UI-001`, replay with another file of the folder chosen in the runner. With the product as case data too, the step holds `testdata/dat/${param:product}/${param:datFile}` (still format version 7: `ui.ts` replaces the longest value first and also inside a text that already holds a placeholder). **Runner**: under `D` the params that name a part of a data file path are asked last and in the order of the path (`choiceOrder`, `choicesOf(doc, params)` in `runner/lib/settings.js`): the product = the folders of `testdata/dat/`, then the dat file = the files of the chosen product's folder; after another product was chosen the old file name cannot be kept: a single file is taken by itself, otherwise the PO must pick. An older version 7 runner runs such a case as exported but offers no list. **The names of the real variant files are not known**: only `<PRODUCT>.dat` is referenced in `testdata/`; the user copies the files.
- **The `Given` trade of a lifecycle event has a trade type** (explicit user requirement: the events run on a normal, a StepIn full or a StepIn partial trade, of any product and dat file). `tradeType` in `shared.given-trade` of `testdata/common.json` is `Normal` (default, also without the value), `StepInFull` or `StepInPartial`; any other value fails the case before the first request. `flows.tradeProvisioning.provisionLiveTrade(product, data)` reads it (`tradeTypeOf`): for a StepIn type the submit carries the `udf` list (`stepInUdf`: `stepInType`, `oldCptyName`, `oldCptyFmId`, `novationDate`), built from `oldCounterpartyName`, `oldCounterpartyFmId` and `novationDate`, which moved from `testdata/trade-approval-reject.json` to the shared block (a missing one fails the case). No spec changed: every event case gets it through its data; a spec's `defaults` or a case's row can set another type for that spec or case. `provisionPendingTrade` is always a normal trade and `provisionPendingStepInTrade(product, type, data)` takes its type from the spec, so the approval cases do not follow `tradeType`. **The trade type is case data the PO can change** (explicit user requirement: the PO chooses it in the runner; `given-trade` holds the data of the three API variants). `provisionLiveTrade` makes it the param `tradeType` and records the `udf` list as a part that depends on it (`byParam(type, TRADE_TYPES, { StepInFull: [...], StepInPartial: [...] })` of `framework/ui.ts`; format version 11, section 5): the case file holds the lists of both StepIn types, the run sends the one of its type and no `udf` at all for `Normal` (what the API does with an empty list is not known). So the three StepIn values must be in the test data whatever type QA runs (a missing one fails the case), and they are case data too. The substep reads `I submit a new <product> <tradeType> trade ...` (`StepInFull trade`, `Normal trade`). **Runner**: `tradeType` is a line of "Case data"; changing it shows the three values (`paramChoicesOf(steps)` in `core/lib/values.js` -> `fixed` in `askSettings`; numbered prompt: number or name, anything else is asked again; keyboard list: a second `pickRow`); a batch runs with the type of the case file. An older runner would send the whole `{ byParam, ... }` object as `udf`: the PO needs a package built from this version. Verified on the mock (which accepts the `udf` list and ignores it; the request body of each type was checked with `resolveDeep` on the exported file): QA run of cancellation `-UI-001` and the four approval cases, replay of the cancellation file as exported, with `StepInFull` (numbered prompt, also a wrong name) and with `StepInPartial` (keyboard list, pseudo-terminal), replay of an approval file with its fixed list. **Not on Windows / Edge.** **Not on the real system**: that a StepIn trade becomes Live through the same approve request, and that each event behaves on a StepIn trade as its flow and checks assume (they were written from the features' normal trades), are inferred.
- **Every case that creates its trade takes the product and the dat file from its case data** (explicit user requirement): `product` and `datFile` are in `shared.given-trade` of `testdata/common.json` (`FX_TRF`, `FX_TRF.dat`) for the specs whose trade comes from the API, and in the row for creation `-UI-004` (`FX_PSCRIPT`). A spec calls `givenProduct(flows, testData<...>(), description)` (`tests/support.ts`): it skips the case while the dat file is missing, makes the product case data and returns `{ product, data }`. So the event case IDs have no product (`TC-TRADE-CANCELLATION-UI-001`, `TC-TRADE-EARLY-TERMINATION-UI-001`, ...; before: `...-FX_TRF-UI-...`; a case file exported under an old ID stays until it is deleted by hand) and the titles and descriptions do not name it. What a case checks that depends on the dat file (the notionals and the equation line of the partial novation, for one) is case data the PO has to change with the file. `[TC-TRADE-CREATION-UI-004]` (this repo's ID) is the creation case for a chosen product and dat file: login, create, pending approval.
- **A case logs in once** (explicit user requirement: one case never needs both the maker and the checker in the browser). What the other role did before is the `Given`: through the API where the request is known (`TradesApi.submit`, `approve`, `reject`), so the checker approving a new trade is `[TC-TRADE-APPROVE-CREATION-UI-001]` (the maker's submit through the API, only the checker logs in) and the former creation case `-UI-005` (maker creates in the browser, checker logs in and approves) is removed. **No API request that leaves a trade with a pending cancellation or a pending amendment is known** (the bodies of `POST /trades/trigger-event` and `POST /trades/<id>/update` were never seen; the mock's are its own), so there only the maker's part of the feature's scenario is a case, ending with "pending checker approval" (`TC-TRADE-CANCELLATION-UI-001`, `TC-TRADE-AMENDMENT-UI-002`. **The checker's decision on a pending cancellation or amendment is no case** (user decision: the checker's approve / reject is the same action whatever is pending, and `TC-TRADE-APPROVE- / REJECT-CREATION-...` cover it); the four cases `TC-TRADE-APPROVE- / REJECT-CANCELLATION- / AMENDMENT-EXISTING-UI-001` were removed, and their exported files stay until they are deleted by hand. `flows.tradeCancellation.expectClosedAsCancelled`, `flows.tradeAmendment.expectLiveAndAmended` and `flows.trades.existingTrade` are kept but used by no case. `flows.tradeAmendment.expectPendingCheckerApproval` checks `PARV` in the blotter row: **inferred** (the status of a pending amendment was not seen). Verified on the mock: the four approve / reject creation cases and cancellation `-UI-001`; the amendment cases are type-checked and listed only. A case file exported under a removed ID (`cases/trade-creation/TC-TRADE-CREATION-UI-005.json`, `cases/trade-cancellation/TC-TRADE-CANCELLATION-UI-002.json`) stays until it is deleted by hand.
- **A case whose `Given` creates its trade can also run on an existing trade** (explicit user requirement: no separate existing-trade cases; before, `tests/existing-trade.spec.ts` held a copy of every case with the `Given` replaced, removed with `testdata/existing-trade.json`, `scripts/export-existing-trade-cases.js`, `scripts/provision/` and `npm run export:existing-trade`; files exported to `cases/existing-trade/` stay until they are deleted by hand). Every spec whose trade comes from the API (cancellation, allocation, amendment, the seven other events, the four approve / reject creation cases) calls `givenTrade(flows, data)` of `tests/support.ts` after `givenProduct`, and its `Given` is `flows.trades.orCreate(() => flows.tradeProvisioning.provisionXxx(...))`; the step lines are unchanged. **Where the ID comes from**: `OREO_TRADE_ID` (applies to every case of the run: set it for one case at a time), else `tradeId` of the case data, else the case creates its trade through the API. Every such case has its own `"tradeId": ""` (explicit user requirement: an event changes its trade, so the next event may not be able to run on it; never commit a real trade ID): in the `defaults` of each event's testdata file, and as a row per case in `testdata/trade-approval-reject.json`. `flows.trades.givenTrade(id)` makes `tradeId` optional case data (`optionalInput` -> `ui.optionalInput`: the given ID, or `''`), and `orCreate(create)` = `ui.onlyWhenEmpty('tradeId', ...)`: the API substeps that create the trade and the substep `I take the new trade as the given trade` (`ui.setParam('tradeId', createdTradeId)`, the action `set`) are recorded in every run with the condition `when: { param: 'tradeId', empty: true }` and executed only while `tradeId` is empty; every later use of the ID is `${param:tradeId}`. So the exported file is the same whichever source QA's run took, with `tradeId` `""`: the PO's replay creates a trade, or uses an ID the PO enters (format version 15, section 5). **There is no check of the state a given trade is in** (the old existing-trade cases checked it after the login; dropped with them): a trade in the wrong state fails at the first step that needs that state. `flows.trades.existingTrade(id)` (`ui.input`: an ID the PO must enter) is kept for a later start state that cannot be created through the API, used by no case. Runner: **for a single case the first question is which trade it runs on** (explicit user requirement: with an existing trade the data to create one is not wanted): `chooseGiven` in `runner/lib/settings.js`, `1` Create a new trade / `2` Use an existing trade (a `pickRow` list on a console; Enter keeps the current choice, the case file's `tradeId`), then `Enter tradeId:` until it gets a value. With an ID, what only the creating substeps use is left out of "Settings for this run" and "Case data", is not asked for and is not in `result.json` or the report (`onlyWhenEmptyOf(steps)` in `core/lib/values.js`: the params and `cfg` entries of the actions with `when: { param, empty: true }` that no other action uses, step lines not counted; for the cancellation the eleven `given-trade` values and `accounts.checker.email`), and `checkCase` does not need the dat file of a substep that will not run. QA's testdata is unchanged: the export records the creating substeps whatever `tradeId` is, so the PO can still choose a new trade. The optional `tradeId` stays a line of "Case data" (`(empty: the case creates a new one)`); changing it asks the same question again. With piped input the choice is one more answer line (Enter = keep). Such a case may be part of a batch, where it creates its trade (`askedParamsOf` leaves out the params of `optionalParamsOf`); a run with an ID does not show the creating actions at all (explicit user requirement: they only confused the reader): the console prints the step line and `- uses the given tradeId <ID>`, the progress counts only the actions that are shown (`[1/20]`), and the report row of the step is `tradeId: <ID> (given for this run)` with the result `Given` and no action list (`given` in `runner/lib/execute.js`, `groupSteps` in `report.js`); `result.json` keeps those actions, with the status `notNeeded` and `given: { tradeId }`. A substep skipped for a value in `when.in` (the allocation's subtrade 3 and 4 of a 2-way split) is not shown either (explicit user requirement): no console line, not counted in the progress, no row in the report's action list (a step line with nothing else is left out of the report); in `result.json` it is `notNeeded` with `hidden: true`. A mandatory `tradeId` (no case has one now) is listed as `(to be entered below)` and asked `Enter tradeId:` until it gets a value; `runBatch` leaves such a case out. Verified on the mock (macOS, Chrome): the cancellation and the four approve / reject creation cases with `tradeId` empty (trade created), and the cancellation with `OREO_TRADE_ID` of a Live trade (no trade created, exported file identical to the one of the run without it); the first question through piped input (both choices, both passed; `result.json` without the hidden data) and the keyboard list through a pseudo-terminal. **Not on Windows / Edge, not on the real system.** A run on a given trade changes its state, so it cannot be repeated on the same trade.
- **Case IDs of the checker's decision and the amendment** (explicit user requirement). - Running cases side by side (QA side only): `playwright.config.ts` sets `fullyParallel: true` and `workers: undefined` (explicit user requirement), so a run takes Playwright's default number of workers (half the CPU cores) unless it is started with `--workers=<n>`, which then runs `n` cases at once (`--workers=1`: one at a time), also cases of the same spec. - **Several cases in one go** (explicit user requirement: pick a folder, or several cases, and run them; in parallel if wanted). The path is under the prefix like every other request (`apiBaseUrl` + `/uc/api/user-preferences`): **confirmed on the real system** by the user's photos of the browser's Network tab (`PUT .../api/v1/uc/api/user-preferences`, JSON body, `X-User-Id`, answer 200 `{ code: 200, status: 'SUCCESS', data: <the preferences> }`). Verified on the mock (creation, cancellation, approval: QA run; replay of the creation file), whose endpoint, now under `/api/v1` too, stores the preferences and changes nothing on its pages. **The fixed request was not run on the real system yet.**

An `api` step gets no screenshot, nor does a `set` (explicit user requirement: the `Given` that creates the trade through the API had a blank screenshot, taken before any page was open, while the same step with a given trade ID had none); its row in `result.json` and the report ends with the values it saved (`(saved: createdTradeId = ...)`). The files its parts send are checked before the run, like uploads.
- Values a step produces (a `read`, a click with `capture`, the `save` of an `api` step: `savedValues` in `core/actions.js`) are displayed, so that the trade a run created can be found in the system (explicit user requirement). QA run: `ui.ts` prints `createdTradeId = TRD-...` and adds a `value` annotation to the test. Runner: the value is printed under the step and again after "Run passed", written to `result.json` (`saved` on the step, `values` on the run) and shown in the report under the BDD step and in a "Values from this run" table after "Case data".
- **The runner never uses a login password from `config.local.json`** (explicit user requirement: whoever replays a case logs in with a password they type; a password in the file must not make a run log in by itself). `main()` blanks every secret entry of the loaded config (`secretEntries`: keys with password / secret / token) in memory, prints a note naming them, and `askSettings` then asks for each required password at the hidden prompt: once per account and window, kept in memory only, never written. The file itself is not modified. Not in `--record` and `--view`: a recording logs nobody in and uses the configured secrets only to mask typed values in its report. QA's Playwright run (`cfg(...)` in `framework/`) still reads the passwords from the file. With piped input the password lines must be part of the input.
- **A dat file can be dropped into the runner's window from anywhere** (explicit user requirement). Where the PO chooses the case data that is a data file's name (`datFile` of `testdata/dat/${param:product}/${param:datFile}`: the keyboard list, where `pickRow({ typing: true })` collects what the console types and shows `File: <path>` with the end of a long path; the numbered prompt; the free-text prompt when the package has no file of that product), the path of a dropped file (`looksLikePath`, `droppedPath` of `case-list.js`) is taken: `adoptDataFile` in `runner/lib/settings.js` copies it into the folder the case reads it from (`testdata/dat/<PRODUCT>/`, so core still reads only `DATA_DIR`, and the file is in the list of later runs) and chooses it. The name must fit the path (prefix and suffix around the param); a file of that name already there is never replaced: the same content is chosen, another content is refused ("rename yours"). Such a list is shown also when the package has only one file of the product. Verified on the mock (macOS): piped drop at the free-text prompt (a name with a space, in quotes) and run passed; through a pseudo-terminal a drop in the keyboard list with a run that passed, and the refusal of another file with an existing name. **Not on Windows**: that Windows Terminal / cmd type the path of a dropped file, with quotes for a space, is what the case tree already relies on (not tried there either).
- **Going back to the case list before a run** (explicit user requirement: a case chosen by mistake could not be left). `askSettings` returns `BACK` (`runner/lib/settings.js`) and `runCase` / `runBatch` pass it on; `main()` then shows the case list again without the "choose another case" prompt. Esc in the first question (`chooseGiven(k, true)`: which trade the case runs on) and in the list of settings and case data (where Esc did nothing before); `B` (or `back`) at the numbered prompts of the same two and at the batch's run mode prompt (`isBack`). Not at the password and other typed prompts after the list. Verified on the mock (macOS): piped `B` at both prompts, Esc in both keyboard lists through a pseudo-terminal; **not on Windows**.

In `askSettings`, when `useKeys()`: the lines of "Settings for this run" and "Case data" are rows, the last row `Run the case` (`Run the n cases`) is highlighted first, so plain Enter still starts the run; Enter on a value changes it (`changeSetting`, `changeParam`: a text or a password is typed at the usual prompt, a product or dat file is picked from a second `pickRow` list, where Esc keeps the current value only when it is still valid) and the list comes back on `Run the case`; `S` starts step by step; Esc does nothing; Ctrl+C closes the window as at a prompt. The prompt is `Press Enter to continue ..., or type a number (1-n) to change that value`: a number (or several, `2 5`) asks for just that value (`changeSetting`, `changeParam`; Enter keeps it), the lists are shown again, and plain Enter starts the run. **The letters `C`, `D` and `CD` no longer exist**; where this file still says "`C` changes" or "under `D`", read "its number in the list". `S` (step by step) is still taken at this prompt. A product or dat file is still chosen from what the package has, and after another product the dat file is chosen again right away (a single file is taken by itself). A batch numbers the settings only. With piped input the lines are answers to these prompts; an input that ends leaves the loop. Verified on the mock with piped input (change product and dat file, settings, several numbers, a wrong answer, no change, ended input); **not on Windows / Edge**.
- When settings are already provided, the runner shows them and lets the PO type `C` to change `baseUrl` and the non-secret account fields; changing the address or an account clears the matching saved password so it is asked for again. The required passwords are listed too, masked (`******` / `(not set)`), and `C` also asks for each password that is set (hidden; Enter keeps it), because a password typed in for an earlier case of the window is reused without asking. A change stays for the cases run later in the same window. Passed and failed runs alike. Not kept open: batches, piped input, a run with video (the file is only written when the browser closes), a run that ended with a runner error. A browser the PO closed by hand is noticed (`isConnected`) and the usual prompt is shown. Verified on the mock through a pseudo-terminal (pass, fail, Ctrl+C); **not on Windows / Edge**.
- **One window runs as many cases as the PO wants** (explicit user requirement: not one window per case). On a console `main()` loops: choose a case (or several), run it, "Press Enter to choose another case, or type Q to close", back to the list. `config` is the same object for every run, so what was typed in (address, account, password) is asked for once; a password stays in memory only. The list comes back as the PO left it (`tree` for the tree; `place` for the numbered list: the folder, the folders above it and the search text). The view server is started after the first finished run and kept until the window closes, so the links of every run of the window work. The prompt text is unchanged for a case without params. The run's data goes to `result.json` (`caseData`, with `changedFrom` for a changed value) and to a "Case data" block in the report.

Step-by-step mode (stops before each titled group and substep) still exists but **is not offered on the screen** (explicit user requirement: the prompt "type S to run step by step" was noise): typing `S` at the settings prompt (`askSettings`, "Press Enter to continue ...") turns it on, for one case or for a batch, which then runs one after another; a case starts right after that prompt, with no separate "Press Enter to run". Verified on the mock (macOS, Chrome, headed): cancellation replay passed, 20 screenshots all full window size, frame visible. **Not on Windows / Edge**; the PO needs a package built from this version.

Verified headless on the mock's report (Chrome); not on Edge), `result.json` (still one entry per action), `step-XX.png` (one per action), `trace.zip`.
- Recording (`runner.js --record`, `record-session.bat`, `npm run record`): no case is run; the browser opens on `baseUrl` with tracing on and the PO works by hand, to report a bug. A trace only lists actions made through Playwright, so an init script in every page (`watchUserActions`) reports clicks, entered values and Enter through `exposeBinding`; each report becomes a `tracing.group(...)` entry with a screenshot inside it (which gives the trace a page snapshot) and a row in the report. It is evidence only: no case file is produced. Password fields and values equal to a configured secret are masked in the report; the trace still contains them.
- Links: the runner starts a local-only http server (`127.0.0.1`, port `evidence.viewPort` or `OREO_VIEW_PORT`, default 9400) that serves `/evidence/*` and Playwright's own trace viewer from `playwright-core/lib/vite/traceViewer` at `/trace/*`. The console and the report footer show the report URL and the "Full replay" trace viewer URL (`/trace/index.html?trace=<url of trace.zip>`). On a console the server lives until the window is closed (`--view` and `--record`: until the PO presses Enter); with piped input the runner exits right away. `--view` (view-trace.bat) serves an index of all runs. `trace.playwright.dev` is opt-in (`evidence.traceViewer: "official"`, which also turns on CORS for `/evidence/*`), because the intranet probably cannot reach it; it has no upload feature, it only reads the local `trace.zip` through `?trace=`. ## 5. Case file format (formatVersion 1 to 15)

```json
{
  "name": "...", "description": "...",
  "requiredConfig": ["accounts.maker.email", "accounts.maker.password"],
  "params": { "counterpartyName": "10 AM NY" },
  "scenario": ["When maker is logged in to the trade portal", "And creates a new trade", "Then the trade is in the blotter"],
  "steps": [
    { "step": "When maker is logged in to the trade portal", "actions": [
      { "substep": "I log in as maker", "actions": [
        { "action": "goto", "value": "/login" },
        { "action": "fill", "target": { "testId": "login-email-input", "inner": "input" }, "value": "${cfg:accounts.maker.email}" }
      ] }
    ] },
    { "step": "And creates a new trade", "actions": [
      { "action": "fill", "target": { "testId": "counterparty", "inner": "input" }, "value": "${param:counterpartyName}" },
      { "action": "read", "target": { "testId": "trade-id" }, "saveAs": "tradeId" }
    ] },
    { "step": "Then the trade is in the blotter", "actions": [
      { "action": "click", "target": { "text": "${var:tradeId}" } },
      { "action": "click", "button": "right", "target": { "testId": "all-trades", "inner": "role=row", "hasText": "${var:tradeId}", "nth": 0 } }
    ] }
  ]
}
```

- **No `formatVersion` and no `source` in a case file** (explicit user requirement: the PO has no use for them; `exportedAt` stays). The format still has versions, in the code (`FORMAT_VERSION`) and in this section, but an export does not write its number: a file without one is read as the current format (nested steps are recognized by their shape, `flatSteps`), and a file that still has a number is checked as before. **What is lost**: a runner older than the file can no longer refuse it with "ask QA for the current package"; a package built before version 10 fails such a file at its first step with an unclear message, so the PO must have the current package. The report shows "Case source" only for a file that has it.
- **No `codeVersion` in a case file** (explicit user requirement: the PO has no use for it): an export no longer writes the Git commit it was made from. A file exported earlier still has the field and the runner still copies it to `result.json`. `formatVersion` stays: it is what lets a runner refuse a file newer than itself with a message asking for the current package, instead of failing on a step it does not understand.
- **Case data that may stay empty, and a value set at run time (version 15, explicit user requirement: a case on an existing trade uses the trade ID it is given, or creates a trade when it is empty).** A condition may be `when: { "param": "tradeId", "empty": true }`: the substep runs only while the param's value of the run is empty, otherwise it is `notNeeded` and, in the runner, not shown (the step's row names the given value instead; section 3). The action `{ "action": "set", "param": "tradeId", "value": "${var:createdTradeId}" }` sets the case data of the run to the resolved value (shown as `Take <value> as tradeId`; not listed with the values of the run, explicit user requirement: it repeated `createdTradeId`, so `savedValues` returns nothing for it). A param named by an `empty` condition is optional (`optionalParamsOf` in `core/lib/values.js`): the runner does not ask for it and runs it in a batch. Writer: `ui.optionalInput`, `ui.onlyWhenEmpty`, `ui.setParam` (`framework/ui.ts`); a step that is recorded but not executed returns the placeholders of what it would have saved (`${var:createdTradeId}`), so the flow goes on. Reader: `isCondition`, `conditionHolds` (`core/lib/values.js`), the `set` case of `executeStep` (`core/lib/execute.js`). **An older runner runs every substep and does not know `set`**: the PO needs a package built from this version.
- **An `api` step names its request (version 14, explicit user requirement: the request bodies confused the PO reading a case file).** The case file holds `{ "action": "api", "ref": "post-trades-create-f8c19c6c" }`; the request is `requests/<ref>.json` of the package: `{ "method", "path", "base"?, "headers"?, "body"?, "multipart"?, "save"?, "timeout"? }` (the step's `value` is `path` there). Everything else of the step (`when`) stays in the case file. Writer: `UI.toRef` in `framework/ui.ts`, at export only: the run, `params`, `requiredConfig` and the data files are worked out from the full steps; the name is method + path (placeholders and query left out) + 8 characters of the SHA-1 of the request, since one path is sent with different bodies. Reader: `readCase(doc, rootDir)` -> `expandRequests` (`core/lib/case-format.js`) puts the request back into the step when the case file is read, so execution, `checkCase`, `paramChoicesOf`, `describeStep`, the report and `result.json` see the full step as before; a missing or badly named request fails the case at reading with "Ask QA for the current UAT-Runner package". A file with inline requests (up to version 13) runs as before. Consequences: a case file is no longer self-contained: a new or changed request needs `requests/` sent along (or a new package), and a case file dropped from elsewhere still takes its requests from the package. Values from test data are params and do not change the request file; a literal (`premiumAmount`, the reset defaults) does. Verified on the mock (macOS, Chrome): QA export of the cancellation (three request files, `requiredConfig` and `params` unchanged), runner replay of it, of the same file with inline requests and of one naming a missing request; `build:portable` copies `requests/`. **Not on Windows / Edge.**
- **A substep that runs only for some values of case data (version 13, explicit user requirement: one allocation case for 2, 3 or 4 subtrades).** A substep entry may carry `when: { param, choices, in }`: `{ "substep": "I fill in subtrade 3", "when": { "param": "allocationWays", "choices": ["2", "3", "4"], "in": ["3", "4"] }, "actions": [ ... ] }`. Its actions run only when the param's value of the run is in `in`; otherwise the runner skips them without showing them (no console line, not counted in the progress, not in the report, no screenshot, not a failure; a step line whose actions are all skipped is left out; `result.json` keeps them with the status `notNeeded` and `hidden: true`; section 3). A value that is not in `choices`, or a param the file does not have, fails the step. `choices` is what the runner offers for that param (`paramChoicesOf`), shown without numbers when the values are numbers themselves (a typed `4` is the value 4). In the flat list every action of the substep carries the `when` (`flatSteps`). Writer: `ui.onlyWhen(param, choices, values, fn)` (`framework/ui.ts`): it records the actions of `fn` whatever the value, so the file holds every variant, and executes them only when the value of QA's run is in `values`; not nested, and the param must be a `${param:...}` of `this.params(data)`. Reader: `isCondition`, `conditionHolds` (`core/lib/values.js`), `runner/lib/execute.js`, `report.js`. **An older runner ignores `when` and runs every substep** (it would fill a third row of a 2-way allocation and fail): the PO needs a package built from this version. Verified on the mock: QA export with the value 2 and 3 (identical steps), replay with 2 (skipped), 3 (run), a wrong value (asked again). **Not on Windows / Edge.**
- **An `api` step outside the prefix (version 12).** `"base": "origin"` on an `api` step joins its `value` to the server of `apiBaseUrl` (scheme, host and port, `new URL(apiBaseUrl).origin`) instead of to `apiBaseUrl` with its prefix: `{ "action": "api", "method": "PUT", "value": "/uc/api/user-preferences", "base": "origin", ... }`. Any other value of `base` fails the step. No request uses it any more: the preference reset it was written for is under the prefix after all. Writer: `base` of `ApiCall` / `ApiRequest` (`framework/ui.ts`); reader: `callApi`, `originOf` in `core/lib/requests.js`. A full address is still refused. `FORMAT_VERSION` is 12; a version 11 runner does not refuse such a file (an export writes no version number) but sends the request under the prefix and fails with a 404: the PO needs a package built from this version.
- **A part of an `api` step that depends on case data (version 11, explicit user requirement: the PO chooses the trade type).** Anywhere in the `headers`, `body` or a JSON part of an `api` step, an object with exactly the keys `byParam`, `choices` and `values` stands for one of several variants: `"udf": { "byParam": "tradeType", "choices": ["Normal", "StepInFull", "StepInPartial"], "values": { "StepInFull": [ ... ], "StepInPartial": [ ... ] } }`. When the step runs it is replaced by the entry of `values` under the current value of that param (placeholders inside it are resolved as usual); a choice without an entry leaves the key, or the list item, out of the request; a value that is not in `choices` fails the step (`Case data tradeType is "X": it must be one of ...`), as does a param the file does not have. `choices` is also what the runner offers for that param. Writer: `byParam(param, choices, values)` in `framework/ui.ts` (`Switch<T>`; `mapTexts` rewrites only inside `values`; `usedParams` adds the param, after those the placeholders use). Reader: `isSwitch`, `resolveDeep`, `paramChoicesOf` in `core/lib/values.js`. An object that happens to have exactly these three keys cannot be sent as it is. `FORMAT_VERSION` was 11 with it; since an export writes no version number, a version 10 runner does not refuse such a file but sends the object itself.
- **Nested substeps and the `scenario` list (version 10, explicit user requirement).** Inside a step entry's `actions`, a substep is an entry of its own, `{ "substep": "I log in as maker", "actions": [ ... ] }`, instead of a field on the first action of its group; it holds the actions up to the next substep or the end of its step line, and actions before the first substep stay directly in the step entry. `scenario` is the list of the step lines alone, with the case data of the file filled in (`a Live 'FX_TRF' trade ...`, where `steps` holds `${param:product}`); case data that is entered per run stays a placeholder. It is for the reader only: the runner ignores it and takes the lines from `steps`, so they follow the data of the run. (A `scenario` list existed for a moment before version 9 and was dropped when the steps became nested; it is back because the user missed it.) **Every export was version 10 from then on** (now 11; `exportCase`, `nested` in `ui.ts`; `flatSteps` in `core/actions.js` reads both levels), so a version 9 runner refuses a new file: the PO needs a new package. Verified on the mock: QA export of a creation and a cancellation case, replay of the creation case in the runner (same 21 actions, 3 step lines, 6 substeps as before), and the flat list of the cancellation case equal to that of its version 9 file. **Not on Windows / Edge.**
- **Nested steps (version 9, explicit user requirement: the feature's step lines must not be mixed into the actions).** `steps` is one entry per step line of the scenario, `{ "step": "When ...", "actions": [ ... ] }`, in order; `actions` are the actions behind that line, each as before (`action`, `target`, `value`, ..., and `substep` on the first action of a group a flow opened). Actions recorded before the first step line are an entry without `step`. From version 9 on every export has the current version: the rule "lowest version that can express the case" ended with it. Up to version 8 `steps` is the flat list of actions and the step line is the `title` of the first action of its group. The runner still works on the flat list: `readCase(doc)` / `flatSteps(steps)` in `core/actions.js`, called where a case file is parsed (`case-list.js`, `case-tree.js`), turn the nested entries into it (the step line becomes the `title` of the entry's first action), so a version 1 to 8 file runs as before and nothing else in the runner, `result.json` or the report changed. A file that mixes entries and plain actions is refused. Verified on the mock: QA export, replay of the nested file and of a flat version 7 copy of it (same 21 actions, same three report rows), refusal of a newer version. **Not on Windows / Edge.** A hand-written or older case file under `cases/` stays flat until it is exported again.
- Versions before 9: 1 = steps only; 2 = adds the `params` block and `${param:name}`; 3 = adds `hasText` in a target and `button` on a click; 4 = adds the `api` action; 5 = adds `request` on a click; 6 = adds case data without a value (`"tradeId": ""` in `params`), which the runner asks for before the run; 7 = adds `${param:name}` in the name of a data file (`testdata/dat/${param:product}/${param:datFile}`) and in `title` / `substep`; 8 = adds the actions `expectHidden`, `expectEnabled`, `expectDisabled`, `expectValue`. Until version 8 a case was written in the lowest version that could express it (8 when a step is one of those four actions, otherwise 7 when a data file name or a step line holds a param, otherwise 6 when a param has no value, otherwise 5 when a click has a `request`, otherwise 4 when it has an `api` step, otherwise 3 when a step has `button` or a target has `hasText`, otherwise 2 with case data, otherwise 1), so the export of an existing case is unchanged and an older runner still runs it. `FORMAT_VERSION` in `core/actions.js` (15) is the highest version the code runs; the runner refuses a newer file with a message asking for the current package.
- `click` may carry `request` (written by `ui.clickAndAwait`): `{ "url": "/trades/${var:createdTradeId}/calculate-risk", "method": "POST", "setting": "riskEngine", "mock": { "status": 200, "body": { ... } } }`. The step clicks and waits for the answer of that request (`url` is matched like the one of `capture`; placeholders are resolved in it and in the texts of the mock body); an answer other than 2xx, or none within `timeouts.response` (or the step's `timeout`), fails it. When the local config entry named by `setting` is `"mock"`, the request is answered with `mock` instead of being sent; without `setting` and `mock` it is always sent. `setting` is added to `requiredConfig`, after the entries the placeholders need. A click cannot have both `request` and `capture`.
- `click` may carry `button: "right"` (written by `ui.rightClick`): a right-click, which opens a context menu such as the action menu of a blotter row. Without it, a normal click.
- **Case data given by its value** (written by `ui.param(name, value)`, in a flow `this.caseData(name, value)`; version 7): what decides the scenario and is normally recorded literally, above all the product, becomes case data the PO can change. After the call every literal use of the value is recorded as `${param:name}` (the rewriting of `ui.input`, which is `ui.param` plus the empty value in the case file), also in the step lines (`title`, `substep`: `creates a new '${param:product}' trade`), which the runner prints and reports with the value of the run (`fillParams`). The data files of a case are checked with the case data of the file before anything is asked and again with the data of the run after `D` (`checkCase(chosen, params)`): under `D` such a param is not free text (explicit user requirement): `choicesOf(doc, params)` lists the values that the package has for that part of the path (the folders of `testdata/dat/` -> the products; the files of the chosen product's folder -> its dat files), numbered, and the prompt takes a number or a name and asks again for anything else. A product without its `.dat` (possible only with piped input that ends) ends the case with `File to upload was not found: testdata/dat/<PRODUCT>/<PRODUCT>.dat`. The file of an `api` part is resolved too. The value must have at least 4 characters. A batch runs with the product of the case file. It is a version of its own because an older runner would look for a file named `testdata/dat/${param:product}/${param:datFile}`. Verified on the mock: QA run, replay as exported and with another product, missing dat file.
- A param with the empty text as value is **entered for every run** (written by `ui.input`, version 6): the runner asks `Enter <name>:` until it gets a value; `resolveValue` fails on a param that is still empty. It is a version of its own because an older runner would run with the empty text, e.g. take the first row of the blotter as the trade's.
- `params`: flat object, name → text. A value may contain `${cfg:path}` (for a value that must not be committed); nothing else is resolved inside a param value.

- Actions: `goto fill click press select upload api read expectVisible expectHidden expectEnabled expectDisabled expectValue expectText expectUrl wait`. `expectHidden`: the element is not shown, or not there at all (a closed dialog, a menu entry that is not offered). `expectEnabled` / `expectDisabled`: whether the control can be used; for a button web component the target is the real button inside it (`inner: 'button'`). `expectValue`: what an input holds (`value`, placeholders resolved), which `expectText` cannot read; the target is the real input (`inner: 'input'`). The four are `V8_ACTIONS` in `core/actions.js`; no committed case uses them yet
- `api` (written by `ui.api`): `{ "action": "api", "method": "POST", "value": "/trades/create?tradeAction=SUBMIT", "headers": { "X-User-Id": "${cfg:accounts.maker.email}" }, "multipart": { "trade": { "json": { "basic": { ... } } }, "datFile": { "file": "testdata/dat/FX_TRF/FX_TRF.dat" } }, "save": { "createdTradeId": "data.trade.id" } }`. `value` is a path joined to `apiBaseUrl` of the local config (a full address is refused when recording, so no server address gets into a case file); `apiBaseUrl` carries the prefix all requests share (`.../api/v1`), so `value` starts after it. The request carries `multipart` (each part `{ json }`, sent as a JSON blob, or `{ file }`, a file inside `testdata/dat/`), or `body` (JSON), or nothing. Placeholders are resolved in `value`, in `headers` and in every text inside `body` and the JSON parts; a number stays a number. `accept: application/json` is sent unless a header overrides it. Any answer other than 2xx fails the step with the status and the first 300 characters of the response; a 404 or an answer that is not JSON adds a hint to check `apiBaseUrl` and its prefix. `save` stores fields of the JSON response (dotted path) as variables, used later as `${var:name}`. Optional `timeout` (ms). The request is sent from Node by the browser context's request client, not by the page.
- `upload`: `value` is a path relative to the root that must be inside `testdata/dat/` (`resolveDataFile`; the runner checks the files exist before prompting). `click` may carry `capture: { url, method, field, saveAs }`: the response of the matching request (path ends with `url`; a query in `url` must match too, since the path alone never contains it) is read in the browser without re-sending it, and `field` of its JSON response is stored as a variable.
- Target fields: `testId | role(+name) | label | placeholder | text | css`, plus `inner`, `hasText`, `nth`, `exact`. They are applied in the order `inner` → `hasText` → `nth`: `hasText` keeps only the elements that contain the text (a part of the text is enough, like Playwright's `filter({ hasText })`), and `inner` may be any Playwright selector, e.g. `role=row`.
- Placeholders: `${cfg:path}` = local config; `${var:name}` = a value read by an earlier `read` or `capture`; `${param:name}` = case data from `params`. **Resolved in both value and target**; `requiredConfig` covers both as well, plus the `${cfg:...}` inside used param values and the headers, body and parts of an `api` step; a case with an `api` step also lists `apiBaseUrl`, first.
- In the recording (`ui.ts`) and in the runner's flat list, `title` is attached only to the first action of each outermost `ui.step()` group, `substep` to the first action of each nested one; the case file holds the title as the `step` of its entry. Step lines are written BDD-style (`Given ...`, `When ...`, `Then ...`); this is plain text in the same field.
- When changing the format, change both `ui.ts` (writer) and `actions.js` (reader), and consider `formatVersion` compatibility.

## 9. Pitfalls already fixed (do not regress)

- The runner reads input through a line queue from `rl[Symbol.asyncIterator]()`; consecutive `rl.question` calls drop lines under piped input and exit silently.
- While a case runs on a console, key echo is muted and lines typed during the run are discarded before the next prompt (`discardTyped`), so a stray Enter cannot skip a pause. This is skipped for piped input, where every buffered line is an intended answer.
- While the case tree is shown, readline must not see the keys (`rl._ttyWrite = () => {}`, removed again when the tree closes): it would echo them, collect them as a typed line that answers the next prompt, and close the input on Ctrl+C or Ctrl+D. The `keypress` events still arrive, which is what the tree listens to. The tree redraws only its own lines (cursor up, erase to the end of the screen), never the whole screen, except after a resize, when the number of lines on the screen is no longer known.
- The readline interface is created with `historySize: 0`. With a history, a password typed at a hidden prompt was a history entry like any other line: the Up key at the next prompt put it on the screen in clear text.
- Ctrl+C at a prompt must not end the input (`rl.close()`): the prompts that have a default (settings, run mode) would take it and the case the PO wanted to give up would run. It exits the process instead. Only a recording ends through `rl.close()`, because there ending the input is how the session is saved.
- A run counts as under way from before its browser is launched (`openRuns++` first), so that Ctrl+C during a slow browser start stops the run instead of being taken for a Ctrl+C at a prompt.
- A case's evidence folder is created only after every prompt has been answered (giving up at a prompt leaves no empty folder), and `evidenceDir` takes the next free second when the name exists: cases that run at the same time start within one second.
- Before the "choose another case" prompt the runner calls `discardTyped()`: an Enter pressed while the case was running would otherwise answer it, and the next one would start a case. A run that ends with an error is cleaned up through `releaseRun` (closes its browser, removes its key handler) before the window goes on, and the loop stops once `inputEnded` is set, or it would spin on an input that has ended.
- When video initialization fails, **close the whole browser and launch again**; closing only the context makes the later `newPage` fail.
- The "no browser found" hint is shown only when `browserType.launch` fails; otherwise it is a false alarm.
- The trace viewer needs http (it registers a service worker), so a `file://` link to it never works; that is why the runner serves it. The Claude desktop preview pane cannot register that service worker either - verify the viewer in a real Chrome / Edge.
- `${var:...}` inside a target must also be resolved in `executeStep` (needed to locate a trade that was just booked).
- In the recording script, typed text is remembered from `input` and reported before the next action (mousedown elsewhere, Enter, focusout, pagehide), not from `change`: `change` is not a composed event, so it never reaches the document from inside a shadow root. Clicks are taken at `mousedown`, because a dropdown closes on mousedown and the `click` then lands on whatever is behind it (`click` is used only for keyboard clicks, `detail === 0`). Labels of shadow buttons come from the host with the testid, since the inner button only holds a slot.
- Response capture pauses the response in the browser through a CDP session (`Fetch.enable` at the `Response` stage, `Fetch.getResponseBody`, then `Fetch.continueRequest`); Chromium only. Do not go back to either alternative: `waitForResponse` / `page.on('response')` lose the body when the page navigates right after the response, and `page.route` + `route.fetch()` re-sends a multipart upload without its file (the real system answers `Invalid dat file: empty or null bytes`). The mock posts real multipart and navigates immediately, so it catches both.

- A flow that provisions data through several API calls must not start while one of its requests is unknown: it would leave a half-prepared trade in UAT on every run. Check for the missing request before the first call (the provisioning flow did so until the approve request was known).
- The prefix `/api/v1` is written once, in `apiBaseUrl`. A path that repeats it is answered with 404, an `apiBaseUrl` without it with a page instead of JSON; the error of an `api` step names both causes.
- A request is mocked for one click only (`page.unroute` in a `finally`): a route left in place would also answer the same request of a later step that is meant to reach the system. The mocked answer carries `access-control-allow-origin` for the page's origin, since the API is on another origin than the pages.
- A text field is filled through `{ inner: INNER_INPUT }`, never on the element the element file names: that element is the `sc-text-input` host, whatever its name says (`..._textarea`), and `fill` on it throws. The mock's text fields are hosts too, so it catches a missing `inner`; a plain `<input>` or `<textarea>` with a testid in the mock would hide it (that is how the comments field of the cancellation got through).
- An API path with a variable (`/tasks/${taskId}/...`) is recorded with `${var:...}` like any other text; do not build it from a value that did not come out of `ui.read` / `ui.api`, or the replay would call the recording's trade.

- The runner's context must not set a fixed `viewport` in a headed window: Chromium then shows the page at that size in the corner and every `page.screenshot` switches it between that size and the window, which the PO sees as flicker. Keep `viewport: null` (`runner/lib/execute.js`; `record.js` had it already).

## 11. Coding conventions

- Reports read as BDD without any BDD framework (playwright-bdd / Cucumber were rejected by the user): the test title is the Scenario, and steps are grouped with `ui.Given / When / Then / And / But(text, fn)` (capitalized, since a lowercase `then` would make `UI` a thenable). The runner emphasizes the keyword in the report.
- **The spec carries the feature's steps** (explicit user requirement: the case must read like the Java `.feature`, with the same step lines): a case is a list of `await When('maker is logged in to the trade portal', () => flows.auth.login('maker'))` lines, using the `Given / When / Then / And / But` fixtures (the step returns the flow's result). Steps nest in two levels like a feature step and its snippet: the outermost step (the case's) is recorded as `title`, i.e. a report row; a step a flow opens inside it is recorded as `substep` (keyword stripped), an optional field on the first action of that group that older runners ignore (no format version change). The runner prints substeps, shows them as headings in the row's action list and stops on them in step-by-step mode. A flow step outside any case step is still a `title`.
- Action flows do not assert their own outcome: the `Then` is a separate `expect...` flow called by the case (`createTrade` then `expectPendingApproval`), so the scenario's expectation is visible in the case.
- Layering: cases call only flows; flows call only page / component / API object operations (never `ui.click / ui.fill / ui.api`, no locators, no request paths) and own the Given / When / Then grouping; pages, components and API objects hold the locators and requests and only atomic operations (no sequences, no BDD keywords). A new page extends `BasePage` and is registered in `App`; a new API object extends `BaseApi` and is registered in `App`; a control shared by pages becomes a component; a new business domain extends `BaseFlow` and is registered in `Flows`.
- Every page action must go through `ui.xxx` (inside a page or component: `this.ui.xxx`); do not use `page` directly, or it will not be recorded.
- An API call goes through an API object in `framework/api/` (`this.ui.api(...)`), never through `page.request` or `fetch` in a flow or a spec, for the same reason. The request (method, path, response fields) is a `static` of the API object; who sends it is `this.as('<role>')`. Only a request whose method, path and body are known from the E2E project or the real system is written, and what was inferred is said in its comment (the body of `TradesApi.approve`); a flow checks for a request that is still unknown before its first call. A path never contains the prefix that `apiBaseUrl` carries (`/api/v1`). Never write a full address, and never the accounts the E2E project's Java source hard-codes.
- A locator is `element('<name>')` with the name from `elements/`, held by the page or component that owns the control. Never edit `elements/` by hand and never invent a name: a new element is added in the E2E project and synced. Until it exists there, write `{ testId: '...' }` (the sync reports it once an element defines that testid). Prefer `data-testid`; when a testid is missing, ask the developers to add one rather than writing brittle CSS/XPath.
- Accounts and passwords always use `cfg('accounts.<role>.password')`; never put a real server address, IP or password into any committed file.
- Case data never goes into `config.local.json` or into a spec as a literal: put it in `testdata/` (values every spec shares in `common.json`, values several specs share in a block of the `shared` section of `testdata/common.json` that each of them lists in `use`, values of one spec in `defaults`, differences in the row; never copy a value from one spec's file into another) and use it in the flow through `this.params(data)`. A flow that needs data takes one typed data object after its scenario arguments (`createTrade(product, data: TradeCreationData)`). `testdata/` is committed: business values only; write `"${cfg:...}"` for anything that must stay local.
- Everything in the repo is written in English: code, comments, console and report text, test titles, step titles, docs.
