# OREO UAT Replay - Project Handover Notes

> Context file for Claude Code. It is read automatically when this project is opened.

## 1. Background and goal

- Project: UAT testing of OREO, a bank-internal system managing the full lifecycle of non-flow FX structured products (TARF, DCD, KO Forward, etc.).
- Role: the user is QA.
- Goal: **QA runs a case locally with Playwright → a "case file" (JSON) is exported automatically → the PO, without writing code or installing anything, double-clicks to really replay that case in the browser on their own computer, to reproduce issues or repeat acceptance.**
- Current status: **the MVP is complete and verified** (log in → land on the Trades page → verify the top-right corner shows the current user), end to end on the mock pages and triggered successfully on the company machine. Trade creation, the checker's approval / rejection and trade cancellation are written and pass on the mock (15 cases); on the real system they are only partly run (section 10, items 4 and 5). Next: connect to the real system.

## 2. Key decisions already made (do not overturn lightly)

| Decision | Reason |
|---|---|
| Use Playwright (cases in TypeScript, runner in plain JS) | Best locators, auto-waiting and trace capability |
| Export **JSON step data**, not code | The PO runs data only: safe and easy to audit; waits, screenshots, browser, etc. are controlled centrally by the runner |
| **QA runs and PO replays share `core/actions.js`** | Guarantees "what ran when it was recorded is exactly what runs on replay" |
| Record at the "action layer" instead of recording mouse clicks | The system is stateful (trade IDs differ every time); click recordings cannot be re-run |
| Server address, accounts and passwords live only in `config.local.json` | Never in code, case files or Git (the real IP seen in screenshot URLs must not appear in the repo) |
| **Case data lives in `testdata/*.json`** (committed) and travels inside the case file as `params` | Different cases need different parameters, so they cannot all sit in one config file; the PO gets the data with the case and can change it for a run. Config is for the environment only |
| The PO side is a **portable folder**: portable `node.exe` + `runner` + `@playwright/test` | The PO cannot install software; uses the machine's own **Edge** (`channel: msedge`), no browser download |
| **No video** by default | Video depends on Playwright's ffmpeg; the company intranet cannot resolve `cdn.playwright.dev`, so the download fails |
| Packaging **copies the local node.exe** instead of downloading Node | The company intranet cannot reach nodejs.org |
| Locators **prefer `data-testid`** | Explicit user requirement; developers already provide testids on key controls |
| **Locators are the E2E project's element JSON**, copied as it is into `elements/` and used by name: `element('new_trade.book_btn')` | Explicit user requirement: do not convert the Java project's locators one by one; a locator is maintained in one place |
| **A trade a case needs beforehand is created through the API**, as an `api` step of the case, sent with Playwright's own request client (`page.request`). The API has no login: the sender is the header `X-User-Id` = that role's e-mail from the local config | Explicit user requirement. Lifecycle events (cancel, approve, step in...) all start from an existing trade; the E2E project provisions it through the API too. Its `RestUtil` is a company-internal Java library and is not used |
| **`FX_CO` is `FX_PSCRIPT`, `FX_FSB` is `FX_PSCRIPT_FSKO`** | Stated by the user: the E2E project's features still list the old names in their Examples; this repo uses only the new ones (registry, case IDs, `data/<PRODUCT>.dat`, API `productId`). Do not add the old names as separate products |
| **English only** across the repo | Explicit user requirement: no Chinese in code, comments, messages, file names, docs or case files |
| Rejected approaches | Intranet server + live noVNC view (user found it too complex); packaging as a Java jar; pure click record-and-replay |

## 3. Architecture

```
QA:  tests/*.spec.ts ─► framework/flows/   ─► framework/pages + components + api ─ui.xxx─► framework/ui.ts (execute + record)
     (case: scenario)   (flow: BDD steps)      (locators / requests + atomic operations)  │ calls
                                                                                    ▼
                                                                              core/actions.js  ◄── shared execution core
                                                                                    ▲
PO:  run-case.bat → runner/runner.js ──reads cases/**/*.json, calls step by step───┘
```

- Page Object Model in three layers, each calling only the one below (QA side only; the case format and the runner know nothing about it). **Page / component** (`framework/pages`, `framework/components`): owns locators as `protected readonly` fields and exposes atomic operations built on `this.ui.xxx` (one field, one button, one dropdown value, one check); a page exposes the components it contains as public fields (`newTrade.confirmDialog.confirm()`); a form with many fields is a table plus one generic operation (`newTrade.setField(name, v)`). **Flow** (`framework/flows`, one class per business domain extending `BaseFlow`, reached through the `flows` fixture as `flows.<domain>.<step>()`): business steps, i.e. the Given / When / Then groups and the atomic operations inside them; each takes an optional keyword. **Case** (`tests/`): only the scenario's steps, each wrapping `flows.<domain>.xxx(...)` calls, and data. `App` (`framework/app.ts`, the `app` fixture) holds one instance of every page and of `TopBar`. The refactoring was verified by exporting all ten cases on the mock before and after: the steps are identical.

- API objects (`framework/api`, QA side only) are the same layer as pages and components: a class per API area extending `BaseApi` holds its requests as `static` (`TradesApi.submit`) and one atomic operation per request, built on `this.ui.api(...)`; `this.as(role)` gives the `X-User-Id` header as `cfg('accounts.<role>.email')`. A flow composes them (`flows.tradeProvisioning.provisionLiveTrade(product, data)`: the maker submits, the checker approves; returns the trade ID); a case never calls them. `ui.api` records an `api` step (section 5) and returns the saved response fields, which are tracked as variables like a `read`. API steps are for preparing data: the `When` and the `Then` of a case stay in the browser, or the PO's replay shows nothing.
- **Risk engine mode** (explicit user requirement: mock or real by configuration, like the E2E project's "configured risk engine mode"). Booking a new trade and triggering an event on a trade make the page call a third-party risk calculation before the confirmation dialog opens; when that engine is slow or down the case fails. `riskEngine` in `config.local.json` is `"real"` (default) or `"mock"`; any other value fails the step. The click that starts the calculation is recorded with the request it triggers (`ui.clickAndAwait(target, request)`, a `request` on the `click` step, section 5; the requests are in `framework/risk-engine.ts`: `RiskCalculation.forNewTrade()`, `RiskCalculation.forTrade(tradeId)`). `real`: the step waits for the system's answer, up to `timeouts.response` (default 60000 ms), and fails on any answer other than 2xx with a hint to the setting. `mock`: the request is answered in the browser (`page.route` + `route.fulfill`, removed again after the click) with the success answer of the E2E project's test data and never reaches the system. The mode is not in the case file: the same file runs either way, QA and PO each with their own config. The case lists `riskEngine` in `requiredConfig`, so the runner shows it under "Settings for this run" and `C` changes it; a run with a mocked request says so on the screen (`NOTE: riskEngine is "mock" ...`), in the step text (`MOCKED`), in `result.json` (`mocked`) and at the top of the report. Verified on the mock in both modes, also with its risk endpoints answering 503 (`MOCK_RISK_ENGINE=down`: `real` fails with the status, `mock` passes), and with a probe for a request to another origin with a preflight. **Not run on the real system.**
- Data-driven cases (QA side): `testdata/common.json` is a flat object shared by all files; `testdata/<name>.json` is `{ "defaults": {...}, "cases": [ { "id": ..., ... } ] }`, all optional. A case is merged common → defaults → row (the row wins). **Data is matched at run time by case ID** (explicit user requirement): a test title starts with its case ID in `[ ]`, which the spec may build (`[TC-TRADE-CREATION-${product}-UI-001]`); the row `id` in testdata is the full ID (`TC-TRADE-CREATION-FX_TRF-UI-001`); the `testData` fixture (`const data = testData<TradeCreationData>()`) looks the title's ID up in `testdata/<spec file name>.json`. A row exists only for a case whose values differ from the shared ones (explicit user requirement: no rows that hold nothing but an id); without a row the case gets common + defaults. Do not generate the cases by looping over the testdata rows. The case hands the data to the flow. In the flow `const p = this.params(data)`: `p.xxx` is recorded as `${param:xxx}` and its value is written to the `params` block of the case file (only parameters that are used, in order of first use); what decides the scenario (the product) stays in the spec, is passed to the flow as a plain argument and is recorded literally. Pages and components are unaffected: their operations take a `Val`.
- Element locators (QA side): `elements/` mirrors `src/test/resources/elements` of the Java + Cucumber E2E project, with the same two folders (`pages/`, `components/`) and file names; each file is a list of `{ "name": "new_trade.book_btn", "lookupDetails": { "findBy": "testId", "value": "create-trade-book-btn" } }`. `element(name, extra?)` (`framework/elements.ts`) turns a name into a `Target`; `extra` (`inner`, `nth`, `exact`) adds what the element files do not know, above all `{ inner: 'input' }` (or `{ inner: INNER_INPUT }`, which also matches a multi-line field), since they only locate the host of a control. Files are read once, on first use; an unknown name, a name defined differently in two files or an unsupported `findBy` (only `testId` so far, `FIND_BY`) fails the case with a clear message, and only for elements that are really used. `npm run sync:elements -- <E2E project>` (or `OREO_E2E_DIR`) mirrors the files (added / changed / removed; it aborts without copying when a file seems to contain a server address) and then checks `elements/` against `framework/`: used names that are undefined fail it, hand-written testids that an element defines are listed with the `element('...')` to use. `OREO_ELEMENTS_DIR` points the loader at another folder. Nothing changes for the PO: a case file holds resolved targets and `elements/` is not packaged. No dynamic (placeholder) locators yet: the E2E project has none that are needed.
- **Cases on an existing trade** (explicit user requirement: an addition to the cases that create their trade, since the PO often wants to go on with a trade already worked on). The ID is case data that is entered for every run: in a flow `flows.trades.existingTrade(id)` -> `this.input('tradeId', id)` -> `ui.input(name, value)`, after which every literal use of the value is recorded as `${param:tradeId}` (the same rewriting as for variables, in `variabilize`), so the flows keep taking `tradeId: string`. `exportCase` writes the param with an empty value (the ID of QA's run is used up) and format version 6. Runner: `askSettings` lists it as `(to be entered below)` and asks `Enter tradeId:` until it gets a value (not offered under `D`); `caseDataOf` does not mark an entered value as changed; `runBatch` leaves such a case out (`askedParamsOf`: "needs tradeId to be entered: run this case on its own"). QA side: the ID comes from the environment variable `OREO_TRADE_ID` (`givenTradeId` in `tests/support.ts`), never from the repo; without it the cases are skipped. These cases are the one exception to "can be repeated": a run changes the trade's state.
- After a test **passes**, `framework/fixtures.ts` exports `cases/<spec name>/<caseId>.json` automatically: one folder per spec, i.e. per lifecycle event (`tests/trade-cancellation.spec.ts` -> `cases/trade-cancellation/`), the same name as its test data file. With about ten events and 18 products there will be hundreds of case files (explicit user requirement: not all in one folder, and the PO cannot be shown them one by one). The folder is only where the file is: the case format has no field for it. An export never moves or deletes a file: a case file exported earlier directly into `cases/` stays there, next to its new copy in the folder, until it is deleted by hand.
- Running cases side by side (QA side only): `playwright.config.ts` sets `fullyParallel: true` and `workers: 1`, so a run is one case at a time unless it is started with `--workers=<n>`, which then runs `n` cases at once, also cases of the same spec. This is possible because a case shares nothing with another one: it has its own browser, `ui` and variables, creates its own trade and exports its own file. A case must stay that way: never let a case use a trade or any other state that another case left behind. With more than one worker each value line in the console starts with its case ID (`[TC-...] createdTradeId = ...`), since the lines of different cases are mixed there. Verified on the mock: 13 cases in 18 s with 4 workers instead of 53 s, the exported case files identical to those of a run one by one. **Not tried on the real system**, where every case logs in with the same account at the same time (section 10). The PO's runner has its own way of running several cases at the same time (the batch, below); the two share nothing.
- The runner reads every case file under `cases/` at any depth and shows them as a **tree that is operated with the keyboard** (`pickCases`; explicit user requirement: only the modules at first, a folder opens to show its cases, the keyboard picks what to run). First screen: the folders only, closed, each with its case count (a single top folder is opened by itself). Up / Down / PageUp / PageDown / Home / End move the highlighted row; Right opens a folder, Left closes it or goes to its parent; Enter on a folder opens or closes it, on a case runs it; typing any character searches (the matching cases stay, in their folders, all shown open; a space cannot be part of the search, since Space ticks), Backspace deletes, Esc clears the search; Ctrl+C closes the window. The description of the highlighted case is shown below the list when the window has 20 rows or more; a list longer than the window scrolls (`... n more above / below`). Case files directly in `cases/` (the layout before folders) are in a row `(not in a folder)` after the folders; without any folder the cases are simply listed. The list is redrawn in place, so what earlier runs printed stays above it. Its state (`tree`: open folders, search, cursor, ticks) is kept while the window is open.
- The tree needs a console that sends single keys and can be redrawn (`useTree`: stdin and stdout are a TTY, at least 15 rows and 60 columns, `OREO_PLAIN_MENU` not set). Otherwise the PO gets the **plain numbered list** (`chooseCase`, the list before the tree, unchanged): a folder shows its sub-folders with their case counts, then the cases directly in it; a number opens a folder or runs a case (plain Enter = number 1), `B` goes back, any other text is a search in the current folder and below it (every typed word must match; digits with a leading zero such as `001` are a search); a list is cut at 40 entries (`LIST_MAX`). It runs one case at a time and has no "run all" entry (not asked for): with it, several cases are run by dragging a folder onto the bat. **With piped input nothing changed**: the numbered list, one choice.
- **Several cases in one go** (explicit user requirement: pick a folder, or several cases, and run them; in parallel if wanted). In the tree Space ticks the highlighted case, or every case of the highlighted folder (`[ ]` none, `[x]` all, `[-]` some); with ticks, Enter runs the ticked cases in the order of the list and clears the ticks; Esc without a search unticks all. A folder or several case files can also be dragged onto `run-case.bat` or passed as arguments (`casesFromArgs`: a folder stands for every case below it). More than one case is a batch (`runBatch`): cases that cannot be run (`checkCase`: newer format version, missing data file) are left out and listed; the settings are asked for once for all cases (`askSettings` over `requiredOf` of every case), and case data cannot be changed (each case runs with the values of its own file); then one prompt chooses the mode: Enter = one after another (each printed as when run alone, `P` pauses), a number from 2 to `MAX_PARALLEL` (8) = that many at the same time (the prompt is skipped for a batch that runs step by step). At the same time each case has its own browser (`launchFor(config, slot)` offsets the windows) and prints only a `started` and a `passed / FAILED` line; `P` and step by step are not available there. A failed case never ends the batch; a browser that cannot be started does (`halt`). Every case still gets its own evidence folder; at the end `evidence/batch_<timestamp>/` is written with `result.json` (`mode: "batch"`, `status`, `parallel`, `stepByStep`, `interrupted`, `cases[]` with `caseFile, caseName, status, durationSec, values, evidence, error`) and `report.html` (one row per case with its result, values and the links to its own report and trace viewer). The batch has passed only when every selected case passed: a case that was left out or not run makes it `failed`. **Running at the same time is opt-in and verified on the mock only** (11 cases, 4 at a time, 18 s): on the real system every browser logs in with the same account (section 10).
- **Ctrl+C** (`rl.on('SIGINT')`; in the tree the picker handles the key itself, with the same result): while cases run it stops them, a batch still writes its summary (`activeBatch.finish(true)`, which prints the file path of the summary, not a link, since the runner ends at once), exit code 130; while a session is being recorded it ends the session like Enter, so what was recorded is saved; at any other prompt it closes the window with the exit code of the session (1 when a run of the window failed, otherwise 0) and runs nothing.
- A case with an `api` step needs `apiBaseUrl` (first entry of its `requiredConfig`): the runner asks "Enter the API address, with its path prefix" when it is missing and offers to save it like the system address. **`apiBaseUrl` ends with the prefix every request shares (`.../api/v1`); the paths in `framework/api/` and in case files start after it** (explicit user requirement). An `api` step gets no screenshot; its row in `result.json` and the report ends with the values it saved (`(saved: createdTradeId = ...)`). The files its parts send are checked before the run, like uploads.
- Values a step produces (a `read`, a click with `capture`, the `save` of an `api` step: `savedValues` in `core/actions.js`) are displayed, so that the trade a run created can be found in the system (explicit user requirement). QA run: `ui.ts` prints `createdTradeId = TRD-...` and adds a `value` annotation to the test. Runner: the value is printed under the step and again after "Run passed", written to `result.json` (`saved` on the step, `values` on the run) and shown in the report under the BDD step and in a "Values from this run" table after "Case data".
- **The runner never uses a login password from `config.local.json`** (explicit user requirement: whoever replays a case logs in with a password they type; a password in the file must not make a run log in by itself). `main()` blanks every secret entry of the loaded config (`secretEntries`: keys with password / secret / token) in memory, prints a note naming them, and `askSettings` then asks for each required password at the hidden prompt: once per account and window, kept in memory only, never written. The file itself is not modified. Not in `--record` and `--view`: a recording logs nobody in and uses the configured secrets only to mask typed values in its report. QA's Playwright run (`cfg(...)` in `framework/`) still reads the passwords from the file. With piped input the password lines must be part of the input.
- When settings are already provided, the runner shows them and lets the PO type `C` to change `baseUrl` and the non-secret account fields; changing the address or an account clears the matching saved password so it is asked for again. The required passwords are listed too, masked (`******` / `(not set)`), and `C` also asks for each password that is set (hidden; Enter keeps it), because a password typed in for an earlier case of the window is reused without asking. A change stays for the cases run later in the same window. Afterwards the runner offers to save the typed-in address and account to `config.local.json` (default No); it never writes a password, only blanks one that no longer matches.
- **The browser stays open after a single case** (asked for by the user: it used to close the moment the run ended, so the PO could not look at the result or at the page a step failed on). `runCase` passes `keepOpen: interactive`; `executeCase` then stops the trace and writes the report as before but does not close the browser and returns it (`browser`); `main()` prints that it stays open and that what is done there is in no report or trace, and closes it after the "Press Enter to close the browser and choose another case" prompt (also on `Q`; Ctrl+C ends the process, which closes it). Passed and failed runs alike. Not kept open: batches, piped input, a run with video (the file is only written when the browser closes), a run that ended with a runner error. A browser the PO closed by hand is noticed (`isConnected`) and the usual prompt is shown. Verified on the mock through a pseudo-terminal (pass, fail, Ctrl+C); **not on Windows / Edge**.
- **One window runs as many cases as the PO wants** (explicit user requirement: not one window per case). On a console `main()` loops: choose a case (or several), run it, "Press Enter to choose another case, or type Q to close", back to the list. `config` is the same object for every run, so what was typed in (address, account, password) is asked for once; a password stays in memory only. The list comes back as the PO left it (`tree` for the tree; `place` for the numbered list: the folder, the folders above it and the search text). The view server is started after the first finished run and kept until the window closes, so the links of every run of the window work. A case that cannot be run (newer format version, missing data file, browser closed by hand) prints "Runner error: ..." and ends that case, not the window. Exit code: 2 = no cases at the first list, 1 = a case failed or could not be run, otherwise 0. **With piped input nothing changed**: one choice (a case, or the cases given as arguments), no extra prompt, and an error ends the runner with exit code 3.
- A case with `params` gets a "Case data" list at the same prompt; `D` changes values for that run only (`CD` does both; the case file is never modified). The prompt text is unchanged for a case without params. The run's data goes to `result.json` (`caseData`, with `changedFrom` for a changed value) and to a "Case data" block in the report.
- Pausing is a runner-only feature (the case format has no pause action): on a real console pressing `P` pauses after the current step; Enter resumes. Step-by-step mode (stops before each titled group and substep) still exists but **is not offered on the screen** (explicit user requirement: the prompt "type S to run step by step" was noise): typing `S` at the settings prompt (`askSettings`, "Press Enter to continue ...") turns it on, for one case or for a batch, which then runs one after another; a case starts right after that prompt, with no separate "Press Enter to run". Pauses only happen between steps, are recorded per step (`pausedSec`) and excluded from the reported duration.
- Every replay produces `evidence/<caseId>_<timestamp>/`: `report.html` (one row per BDD step, i.e. per titled group, with its result and screenshot; the actions behind it are in a collapsed list, opened automatically for a failed step), `result.json` (still one entry per action), `step-XX.png` (one per action), `trace.zip`.
- Recording (`runner.js --record`, `record-session.bat`, `npm run record`): no case is run; the browser opens on `baseUrl` with tracing on and the PO works by hand, to report a bug. A trace only lists actions made through Playwright, so an init script in every page (`watchUserActions`) reports clicks, entered values and Enter through `exposeBinding`; each report becomes a `tracing.group(...)` entry with a screenshot inside it (which gives the trace a page snapshot) and a row in the report. Output is `evidence/recording_<timestamp>/` with `report.html`, `result.json` (`mode: "recording"`), `step-XX.png`, `trace.zip`. It ends on Enter or when the browser window is closed. It is evidence only: no case file is produced. Password fields and values equal to a configured secret are masked in the report; the trace still contains them.
- Links: the runner starts a local-only http server (`127.0.0.1`, port `evidence.viewPort` or `OREO_VIEW_PORT`, default 9400) that serves `/evidence/*` and Playwright's own trace viewer from `playwright-core/lib/vite/traceViewer` at `/trace/*`. The console and the report footer show the report URL and the "Full replay" trace viewer URL (`/trace/index.html?trace=<url of trace.zip>`). On a console the server lives until the window is closed (`--view` and `--record`: until the PO presses Enter); with piped input the runner exits right away. `--view` (view-trace.bat) serves an index of all runs. `trace.playwright.dev` is opt-in (`evidence.traceViewer: "official"`, which also turns on CORS for `/evidence/*`), because the intranet probably cannot reach it; it has no upload feature, it only reads the local `trace.zip` through `?trace=`. Never upload a trace.zip to a public host: it contains the server address, screenshots, network traffic and typed passwords.

## 4. Layout and responsibilities

| Path | Responsibility |
|---|---|
| `core/actions.js` | Execution core: `FORMAT_VERSION`, `resolveTarget`, `resolveValue` (placeholders), `showPlaceholders`, `executeStep` (with `callApi` for the `api` action), `resolveUrl`, `savedValues` (the values a step produced, for display), `describeStep`, `dataFilesOf` (the `data/` files a step uploads or sends). **Keep it CommonJS and dependent only on `@playwright/test`** (it is bundled into the runner) |
| `core/config.js` | Reads `config.local.json` (overridable with `OREO_UAT_CONFIG` / `OREO_BASE_URL` / `OREO_API_BASE_URL`), `launchOptions`, `secretEntries`. Defaults include `riskEngine: 'real'` and `timeouts: { step: 15000, response: 60000 }`. `apiBaseUrl` is the address of the API including the prefix its requests share (`.../api/v1`, with or without a trailing slash); it has no fallback to `baseUrl`, since the API is on another origin |
| `framework/api/` | API objects: `base.api.ts` (`BaseApi` with `as(role)` = the `X-User-Id` header), `trades.api.ts` (paths start after the prefix that is part of `apiBaseUrl`. `TradesApi.submit` = `POST /trades/create?tradeAction=SUBMIT`, multipart parts `trade` (JSON `{ basic }`) and `datFile`, saving `createdTradeId` = `data.trade.id` and `createdTaskId` = `data.checkerContext.taskId`: confirmed on the real system and in `TradeProvisioningSteps`. `TradesApi.approve(taskId)` / `TradesApi.reject(taskId)` = `POST /checker/tasks/<taskId>/approve` / `.../reject`, from the user's photos of the browser's Network tab; **their body `{}` is inferred** from the JSON content type and the content length of 2, the payload itself was not seen. Operations: `submitTrade`, `approveTask`, `rejectTask`; no case uses `rejectTask` yet), `index.ts` |
| `framework/components/` | **Operations from the E2E project's component snippets that no flow uses yet** (written from the user's photos, type-checked only, their elements not in the partial `elements/`): `ConfirmDialog.expectHidden`; `CheckerAction.expectApproveHidden / expectRejectHidden / expectDialogHidden`; `AllocationDialog` (`allocation-dialog.ts`, `app.allocationDialog`: `typeSplitNumber`, `typePercentage`, `clickAllocate`, `clickAddSubtrade`, `expectRemaining`, `expectTotalPct`, `expectAddSubtradeEnabled / Disabled`); `DynamicAction` (`dynamic-action.ts`, `app.dynamicAction`, a `ConfirmDialog` on `dynamic_action.dialog / confirm_btn`: the dialog of the lifecycle events started from a row's action menu; its text fields are the table `DynamicAction.fields` operated by `typeField(name, value)`, plus `selectPortfolio`, `selectCounterparty`, `openDirection`, `chooseOption`, `expectEquationContains`). ## 5. Case file format (formatVersion 1 to 8)

```json
{
  "formatVersion": 2, "name": "...", "description": "...",
  "source": "tests/trade-creation.spec.ts › ...", "codeVersion": "git:abc123",
  "requiredConfig": ["accounts.maker.email", "accounts.maker.password"],
  "params": { "counterpartyName": "10 AM NY" },
  "steps": [
    { "title": "When maker is logged in to the trade portal", "substep": "I log in as maker", "action": "goto", "value": "/login" },
    { "action": "fill", "target": { "testId": "login-email-input", "inner": "input" }, "value": "${cfg:accounts.maker.email}" },
    { "action": "fill", "target": { "testId": "counterparty", "inner": "input" }, "value": "${param:counterpartyName}" },
    { "action": "read", "target": { "testId": "trade-id" }, "saveAs": "tradeId" },
    { "action": "click", "target": { "text": "${var:tradeId}" } },
    { "action": "click", "button": "right", "target": { "testId": "all-trades", "inner": "role=row", "hasText": "${var:tradeId}", "nth": 0 } }
  ]
}
```

- Versions: 1 = steps only; 2 = adds the `params` block and `${param:name}`; 3 = adds `hasText` in a target and `button` on a click; 4 = adds the `api` action; 5 = adds `request` on a click; 6 = adds case data without a value (`"tradeId": ""` in `params`), which the runner asks for before the run; 7 = adds `${param:name}` in the name of a data file (`data/${param:product}.dat`) and in `title` / `substep`; 8 = adds the actions `expectHidden`, `expectEnabled`, `expectDisabled`, `expectValue`. A case is written in the lowest version that can express it (8 when a step is one of those four actions, otherwise 7 when a data file name or a step line holds a param, otherwise 6 when a param has no value, otherwise 5 when a click has a `request`, otherwise 4 when it has an `api` step, otherwise 3 when a step has `button` or a target has `hasText`, otherwise 2 with case data, otherwise 1), so the export of an existing case is unchanged and an older runner still runs it. `FORMAT_VERSION` in `core/actions.js` (8) is the highest version the code runs; the runner refuses a newer file with a message asking for the current package.
- `click` may carry `request` (written by `ui.clickAndAwait`): `{ "url": "/trades/${var:createdTradeId}/calculate-risk", "method": "POST", "setting": "riskEngine", "mock": { "status": 200, "body": { ... } } }`. The step clicks and waits for the answer of that request (`url` is matched like the one of `capture`; placeholders are resolved in it and in the texts of the mock body); an answer other than 2xx, or none within `timeouts.response` (or the step's `timeout`), fails it. When the local config entry named by `setting` is `"mock"`, the request is answered with `mock` instead of being sent; without `setting` and `mock` it is always sent. `setting` is added to `requiredConfig`, after the entries the placeholders need. A click cannot have both `request` and `capture`.
- `click` may carry `button: "right"` (written by `ui.rightClick`): a right-click, which opens a context menu such as the action menu of a blotter row. Without it, a normal click.
- **Case data given by its value** (written by `ui.param(name, value)`, in a flow `this.caseData(name, value)`; version 7): what decides the scenario and is normally recorded literally, above all the product, becomes case data the PO can change. After the call every literal use of the value is recorded as `${param:name}` (the rewriting of `ui.input`, which is `ui.param` plus the empty value in the case file), also in the step lines (`title`, `substep`: `creates a new '${param:product}' trade`), which the runner prints and reports with the value of the run (`fillParams`). The data files of a case are checked with the case data of the file before anything is asked and again with the data of the run after `D` (`checkCase(chosen, params)`): under `D` such a param is not free text (explicit user requirement): `choicesOf(doc)` lists the values that have a file matching the name in the package (`data/*.dat` -> the products), numbered, and the prompt takes a number or a name and asks again for anything else. A product without its `.dat` (possible only with piped input that ends) ends the case with `File to upload was not found: data/<PRODUCT>.dat`. The file of an `api` part is resolved too. The value must have at least 4 characters. A batch runs with the product of the case file. It is a version of its own because an older runner would look for a file named `data/${param:product}.dat`. Verified on the mock: QA run, replay as exported and with another product, missing dat file.
- A param with the empty text as value is **entered for every run** (written by `ui.input`, version 6): the runner asks `Enter <name>:` until it gets a value; `resolveValue` fails on a param that is still empty. It is a version of its own because an older runner would run with the empty text, e.g. take the first row of the blotter as the trade's.
- `params`: flat object, name → text. A value may contain `${cfg:path}` (for a value that must not be committed); nothing else is resolved inside a param value.

- Actions: `goto fill click press select upload api read expectVisible expectHidden expectEnabled expectDisabled expectValue expectText expectUrl wait`. `expectHidden`: the element is not shown, or not there at all (a closed dialog, a menu entry that is not offered). `expectEnabled` / `expectDisabled`: whether the control can be used; for a button web component the target is the real button inside it (`inner: 'button'`). `expectValue`: what an input holds (`value`, placeholders resolved), which `expectText` cannot read; the target is the real input (`inner: 'input'`). The four are `V8_ACTIONS` in `core/actions.js`; no committed case uses them yet
- `api` (written by `ui.api`): `{ "action": "api", "method": "POST", "value": "/trades/create?tradeAction=SUBMIT", "headers": { "X-User-Id": "${cfg:accounts.maker.email}" }, "multipart": { "trade": { "json": { "basic": { ... } } }, "datFile": { "file": "data/FX_TRF.dat" } }, "save": { "createdTradeId": "data.trade.id" } }`. `value` is a path joined to `apiBaseUrl` of the local config (a full address is refused when recording, so no server address gets into a case file); `apiBaseUrl` carries the prefix all requests share (`.../api/v1`), so `value` starts after it. The request carries `multipart` (each part `{ json }`, sent as a JSON blob, or `{ file }`, a file inside `data/`), or `body` (JSON), or nothing. Placeholders are resolved in `value`, in `headers` and in every text inside `body` and the JSON parts; a number stays a number. `accept: application/json` is sent unless a header overrides it. Any answer other than 2xx fails the step with the status and the first 300 characters of the response; a 404 or an answer that is not JSON adds a hint to check `apiBaseUrl` and its prefix. `save` stores fields of the JSON response (dotted path) as variables, used later as `${var:name}`. Optional `timeout` (ms). The request is sent from Node by the browser context's request client, not by the page.
- `upload`: `value` is a path relative to the root that must be inside `data/` (`resolveDataFile`; the runner checks the files exist before prompting). `click` may carry `capture: { url, method, field, saveAs }`: the response of the matching request (path ends with `url`; a query in `url` must match too, since the path alone never contains it) is read in the browser without re-sending it, and `field` of its JSON response is stored as a variable.
- Target fields: `testId | role(+name) | label | placeholder | text | css`, plus `inner`, `hasText`, `nth`, `exact`. They are applied in the order `inner` → `hasText` → `nth`: `hasText` keeps only the elements that contain the text (a part of the text is enough, like Playwright's `filter({ hasText })`), and `inner` may be any Playwright selector, e.g. `role=row`.
- Placeholders: `${cfg:path}` = local config; `${var:name}` = a value read by an earlier `read` or `capture`; `${param:name}` = case data from `params`. **Resolved in both value and target**; `requiredConfig` covers both as well, plus the `${cfg:...}` inside used param values and the headers, body and parts of an `api` step; a case with an `api` step also lists `apiBaseUrl`, first.
- `title` is attached only to the first action of each outermost `ui.step()` group, `substep` to the first action of each nested one. Titles are written BDD-style (`Given ...`, `When ...`, `Then ...`); this is plain text in the same field, not a format change.
- When changing the format, change both `ui.ts` (writer) and `actions.js` (reader), and consider `formatVersion` compatibility.

## 9. Pitfalls already fixed (do not regress)

- The runner reads input through a line queue from `rl[Symbol.asyncIterator]()`; consecutive `rl.question` calls drop lines under piped input and exit silently.
- While a case runs on a console, key echo is muted and lines typed during the run are discarded before the next prompt (`discardTyped`), so a stray Enter cannot skip a pause. This is skipped for piped input, where every buffered line is an intended answer.
- While the case tree is shown, readline must not see the keys (`rl._ttyWrite = () => {}`, removed again when the tree closes): it would echo them, collect them as a typed line that answers the next prompt, and close the input on Ctrl+C or Ctrl+D. The `keypress` events still arrive, which is what the tree listens to. The tree redraws only its own lines (cursor up, erase to the end of the screen), never the whole screen, except after a resize, when the number of lines on the screen is no longer known.
- The readline interface is created with `historySize: 0`. With a history, a password typed at a hidden prompt was a history entry like any other line: the Up key at the next prompt put it on the screen in clear text.
- Ctrl+C at a prompt must not end the input (`rl.close()`): the prompts that have a default (settings, run mode) would take it and the case the PO wanted to give up would run. It exits the process instead. Only a recording ends through `rl.close()`, because there ending the input is how the session is saved.
- A run counts as under way from before its browser is launched (`openRuns++` first), so that Ctrl+C during a slow browser start stops the run instead of being taken for a Ctrl+C at a prompt.
- A case's evidence folder is created only after every prompt has been answered (giving up at a prompt leaves no empty folder), and `evidenceDir` takes the next free second when the name exists: cases that run at the same time start within one second.
- Before the "choose another case" prompt the runner calls `discardTyped()`: an Enter pressed while the case was running would otherwise answer it, and the next one would start a case. A run that ends with an error is cleaned up through `releaseRun` (closes its browser, removes its key handler) before the window goes on, and the loop stops once `inputEnded` is set, or it would spin on an input that has ended.
- When video initialization fails, **close the whole browser and launch again**; closing only the context makes the later `newPage` fail.
- The "no browser found" hint is shown only when `browserType.launch` fails; otherwise it is a false alarm.
- The trace viewer needs http (it registers a service worker), so a `file://` link to it never works; that is why the runner serves it. The Claude desktop preview pane cannot register that service worker either - verify the viewer in a real Chrome / Edge.
- `${var:...}` inside a target must also be resolved in `executeStep` (needed to locate a trade that was just booked).
- In the recording script, typed text is remembered from `input` and reported before the next action (mousedown elsewhere, Enter, focusout, pagehide), not from `change`: `change` is not a composed event, so it never reaches the document from inside a shadow root. Clicks are taken at `mousedown`, because a dropdown closes on mousedown and the `click` then lands on whatever is behind it (`click` is used only for keyboard clicks, `detail === 0`). Labels of shadow buttons come from the host with the testid, since the inner button only holds a slot.
- Response capture pauses the response in the browser through a CDP session (`Fetch.enable` at the `Response` stage, `Fetch.getResponseBody`, then `Fetch.continueRequest`); Chromium only. Do not go back to either alternative: `waitForResponse` / `page.on('response')` lose the body when the page navigates right after the response, and `page.route` + `route.fetch()` re-sends a multipart upload without its file (the real system answers `Invalid dat file: empty or null bytes`). The mock posts real multipart and navigates immediately, so it catches both.

- A flow that provisions data through several API calls must not start while one of its requests is unknown: it would leave a half-prepared trade in UAT on every run. Check for the missing request before the first call (the provisioning flow did so until the approve request was known).
- The prefix `/api/v1` is written once, in `apiBaseUrl`. A path that repeats it is answered with 404, an `apiBaseUrl` without it with a page instead of JSON; the error of an `api` step names both causes.
- A request is mocked for one click only (`page.unroute` in a `finally`): a route left in place would also answer the same request of a later step that is meant to reach the system. The mocked answer carries `access-control-allow-origin` for the page's origin, since the API is on another origin than the pages.
- A text field is filled through `{ inner: INNER_INPUT }`, never on the element the element file names: that element is the `sc-text-input` host, whatever its name says (`..._textarea`), and `fill` on it throws. The mock's text fields are hosts too, so it catches a missing `inner`; a plain `<input>` or `<textarea>` with a testid in the mock would hide it (that is how the comments field of the cancellation got through).
- An API path with a variable (`/tasks/${taskId}/...`) is recorded with `${var:...}` like any other text; do not build it from a value that did not come out of `ui.read` / `ui.api`, or the replay would call the recording's trade.

## 11. Coding conventions

- Reports read as BDD without any BDD framework (playwright-bdd / Cucumber were rejected by the user): the test title is the Scenario, and steps are grouped with `ui.Given / When / Then / And / But(text, fn)` (capitalized, since a lowercase `then` would make `UI` a thenable). The runner emphasizes the keyword in the report.
- **The spec carries the feature's steps** (explicit user requirement: the case must read like the Java `.feature`, with the same step lines): a case is a list of `await When('maker is logged in to the trade portal', () => flows.auth.login('maker'))` lines, using the `Given / When / Then / And / But` fixtures (the step returns the flow's result). Steps nest in two levels like a feature step and its snippet: the outermost step (the case's) is recorded as `title`, i.e. a report row; a step a flow opens inside it is recorded as `substep` (keyword stripped), an optional field on the first action of that group that older runners ignore (no format version change). The runner prints substeps, shows them as headings in the row's action list and stops on them in step-by-step mode. A flow step outside any case step is still a `title`.
- Action flows do not assert their own outcome: the `Then` is a separate `expect...` flow called by the case (`createTrade` then `expectPendingApproval`), so the scenario's expectation is visible in the case.
- Layering: cases call only flows; flows call only page / component / API object operations (never `ui.click / ui.fill / ui.api`, no locators, no request paths) and own the Given / When / Then grouping; pages, components and API objects hold the locators and requests and only atomic operations (no sequences, no BDD keywords). A new page extends `BasePage` and is registered in `App`; a new API object extends `BaseApi` and is registered in `App`; a control shared by pages becomes a component; a new business domain extends `BaseFlow` and is registered in `Flows`.
- Every page action must go through `ui.xxx` (inside a page or component: `this.ui.xxx`); do not use `page` directly, or it will not be recorded.
- An API call goes through an API object in `framework/api/` (`this.ui.api(...)`), never through `page.request` or `fetch` in a flow or a spec, for the same reason. The request (method, path, response fields) is a `static` of the API object; who sends it is `this.as('<role>')`. Only a request whose method, path and body are known from the E2E project or the real system is written, and what was inferred is said in its comment (the body of `TradesApi.approve`); a flow checks for a request that is still unknown before its first call. A path never contains the prefix that `apiBaseUrl` carries (`/api/v1`). Never write a full address, and never the accounts the E2E project's Java source hard-codes.
- A locator is `element('<name>')` with the name from `elements/`, held by the page or component that owns the control. Never edit `elements/` by hand and never invent a name: a new element is added in the E2E project and synced. Until it exists there, write `{ testId: '...' }` (the sync reports it once an element defines that testid). Prefer `data-testid`; when a testid is missing, ask the developers to add one rather than writing brittle CSS/XPath.
- Accounts and passwords always use `cfg('accounts.<role>.password')`; never put a real server address, IP or password into any committed file.
- Case data never goes into `config.local.json` or into a spec as a literal: put it in `testdata/` (shared values in `common.json` or `defaults`, differences in the row) and use it in the flow through `this.params(data)`. A flow that needs data takes one typed data object after its scenario arguments (`createTrade(product, data: TradeCreationData)`). `testdata/` is committed: business values only; write `"${cfg:...}"` for anything that must stay local.
- Everything in the repo is written in English: code, comments, console and report text, test titles, step titles, docs.
